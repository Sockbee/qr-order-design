## 시험 방식과 중단 조건

5 → 10 → 30 → 50명으로 단계적으로 증가시켰다. 단계 사이에 10초를 두고, SSE 연결 수를 해당 단계 고객 수까지 늘렸다. 각 단계에서 고객당 주문 생성과 주문 목록 조회를 동시에 전송했다. 최초에는 실행 중인 인스턴스가 1개였다.

어떤 요청이든 실패하거나 주문/조회 p95가 5초를 초과하면 이후 단계를 진행하지 않도록 했다. 이미 전송한 단계의 요청은 결과와 DB 반영 여부를 확인하기 위해 완료를 기다렸다. HTTP 요청 제한은 45초, 최대 테스트 주문 시도는 95건이다. readiness는 약 2초 간격으로 조회했다.

## 실패 원인

시험 구간에 운영 애플리케이션 로그에서 `CannotCreateTransactionException` 9건이 확인됐다. 하위 원인은 모두 Hikari 연결 풀의 3초 확보 제한 초과였다. 예:

```text
HikariPool-1 - Connection is not available, request timed out after 3000ms
(total=10, active=10, idle=0, waiting=40)
```

주문 처리의 `visits.lock()`은 모든 테이블에 공통인 `pg_advisory_xact_lock(7319021)`을 사용한다. 해당 트랜잭션이 끝날 때까지 다른 주문이 대기하며, 대기 트랜잭션도 DB 연결을 점유한다. 주문과 조회가 몰리면서 한 인스턴스의 작은 연결 풀이 소진되는 상황과 일치한다. 정확한 개별 잠금 대기 시간은 이번 시험에서 별도 샘플링하지 않았다.

자동 확장도 즉시 도움을 주지는 못했다. 21:04:42에 추가 인스턴스 2개가 시작되었고 startup probe 성공은 각각 21:05:08, 21:05:17이었다. 준비까지 약 26초, 36초가 걸렸다. 36.49초 조회 지연과 시간상 부합하지만, 해당 요청의 전체 분산 추적을 수집한 것은 아니다.

Cloud Monitoring의 1분 샘플에서는 활성 인스턴스가 1개에서 3개로 늘었다. 21:05 샘플의 DB CPU는 약 14.3%, 메모리는 약 29.7%였다. 전체 DB CPU 고갈보다는 애플리케이션 연결 풀과 직렬 처리, 확장 준비 시간이 우선 병목이다. 1분 샘플은 짧은 순간 최대 부하를 모두 보여주지는 않는다.

## 데이터 정합성과 정리

정리 직전 DB에서 다음을 검증했다.

- 테스트 주문 90건 = 성공 응답 90건.
- 고유 `client_request_id` 90개, 고유 주문번호 90개. 중복 및 성공 응답 주문의 저장 누락 없음.
- 전용 테스트 테이블에만 생성된 주문·세션을 대상으로 정리했다. 다른 테이블과 병합되거나 예상하지 않은 주문이 존재하면 정리를 중단하도록 보호했다.
- 정리 수량: 주문 90건, 세션 48개, 테이블 50개, 해당 이벤트 90개, 감사 기록 90개. 주문 항목과 조리 단위는 해당 주문에 연결된 FK cascade로 제거된다.
- 정리 후 테스트 주문 0건, 테스트 테이블 0개를 별도 DB 연결로 확인했다.
- 최종 readiness HTTP 200 / UP.
- 주문번호·이벤트 시퀀스는 되돌리지 않았다. 테스트 성공 주문 90건에 사용한 주문번호는 비어 있게 된다. 실제 주문과 번호 충돌을 피하기 위한 조치다.
