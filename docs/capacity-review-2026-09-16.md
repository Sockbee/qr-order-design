# 50명 동시 주문 용량 검토 — 2026-09-16

판정: 기본 시나리오는 통과했지만 운영에서 50명 동시 주문을 안정적으로 보장할 근거는 아직 부족하다. Cloud Run 연결 용량은 늘어났으나, 모든 테이블이 공유하는 주문 트랜잭션 잠금과 3초 DB 연결 대기가 병목이다. 실제 운영 데이터에 테스트 주문을 생성하거나 배포 설정을 변경하지 않았다.

이 문서 작성 후 사용자의 요청으로 실제 운영 API·DB 시험을 추가 수행했다. 50명 단계에서 주문 45/50건 성공, 5건 실패를 확인했다. 결과와 데이터 정리 내역은 [운영 부하 시험 보고서](production-capacity-test-2026-09-16.md)에 기록했다. 아래 결과는 앞서 수행한 로컬 검토 기록이다.

## 확인한 배포

- 프로젝트 / 리전: `qr-order-507407` / `asia-northeast3`
- 서비스 / 리비전: `qr-order-staging` / `qr-order-staging-00010-kzm`
- 빌드 소스: `b397c90c442d3d65ec1e9d4f00949ab1c19eba57`
- 이미지 digest: `sha256:3cd1933a325ca9e965bddc3c05ca83c65ae5926c93c45925d23607ea43a9eea4`
- 로컬 HEAD `456cb3e`와 배포 소스의 `qr-order-backend` 차이가 없음을 확인했다.
- 동시 요청 100개/인스턴스, 최소 1개, 최대 5개. 각 인스턴스 1 vCPU / 1GiB.
- Cloud SQL: PostgreSQL 17, 1 vCPU / 3.75GiB (`db-custom-1-3840`).
- DB pool: 인스턴스당 10개, 연결 확보 제한 3초. PostgreSQL 이벤트 리스너가 그중 1개를 장시간 사용한다.

500은 최대 확장 시의 설정상 동시 HTTP 요청 용량이다. 초당 500건 주문 처리 성능이나 즉시 준비된 인스턴스 수를 의미하지 않는다. SSE 연결과 일반 API가 같은 용량을 사용한다. 50명 각각의 SSE와 주문이 겹치면 최소 100개 요청이며, 조회와 직원 화면 요청이 추가될 수 있다.

## 운영 관측

20:53 KST까지 최근 2시간 지표에서 현재 리비전은 인스턴스 최대 1개, 인스턴스별 최대 동시 요청 지표 52, CPU 분 단위 평균의 최댓값 약 3.2%, 메모리 약 46%였다. 해당 기간 request_count에는 200 응답만 관측됐다. DB CPU 최댓값 약 12.5%, 메모리 약 30%, 앱 DB 연결 최대 10개였다. 이는 낮은 실제 부하에 대한 관측이지 부하 시험 결과가 아니다.

최근 48시간 요청 로그에서 현재 리비전의 고객 주문 생성은 12건, 모두 200이었다. 중앙값 약 121ms, 최대 약 230ms였다. 조회한 전체 주문 생성 로그에서도 초당 최대 2건이므로 50명 동시 주문을 입증하지 못한다. 애플리케이션 ERROR 로그에서 관측한 예외는 SSE `AsyncRequestTimeoutException`으로, 주문 실패와 구분해야 한다. 최종 readiness는 `UP`이었다.

## 격리한 로컬 HTTP 시험

`FiftyCustomerCapacityTest`는 실제 HTTP 서버와 Testcontainers PostgreSQL 17을 사용한다. 운영과 같은 pool 10개 / 대기 3초를 적용했다. 고객 SSE 50개를 열어 둔 채, 시작 장벽으로 주문 요청 50개를 동시에 보냈다. 각 주문은 메뉴 3종, 합계 13,000원의 테스트 주문이다.

Mac의 CPU·메모리를 Cloud Run의 1 vCPU/1GiB로 제한한 시험은 아니다. 운영 DB 네트워크 지연, Cloud Run 라우팅·확장, 직원 대시보드의 이벤트 후 재조회, 브라우저의 SSE 재연결은 재현하지 않았다. 따라서 아래 지연 시간을 운영 응답 시간으로 해석하면 안 된다.

| 시나리오 | 성공 | p95 | 최대 |
|---|---:|---:|---:|
| 서로 다른 50개 테이블, 1회차 | 50/50 | 445ms | 458ms |
| 서로 다른 50개 테이블, 2회차 | 50/50 | 276ms | 287ms |
| 서로 다른 50개 테이블, 3회차 | 50/50 | 248ms | 258ms |
| 같은 테이블에 주문 50건 | 50/50 | 246ms | 256ms |
| 주문 50건 + 조회 50건: 주문 | 50/50 | 285ms | 299ms |
| 주문 50건 + 조회 50건: 조회 | 50/50 | 278ms | 281ms |

동일 요청 재전송 150건도 모두 성공했고 주문이 추가 생성되지 않았다. 기본 시험 종료 시 신규 주문 250건, 고유 주문번호 250개, 열린 세션 50개, 주문 항목 750개를 검증했다.

## DB 지연 민감도 시험

격리된 테스트 DB의 주문 INSERT 트리거에만 `pg_sleep(0.1)`을 넣어 공통 잠금을 보유하는 시간을 주문마다 100ms 늘렸다. 이는 운영 DB 지연 측정값이 아닌 합성 조건이다.

- 50건 동시 주문: **33건 성공, 17건 HTTP 500**.
- 전체 응답 p95 3,802ms, 최대 4,050ms. 실패 응답도 포함한 수치다.
- 실패는 `CannotCreateTransactionException`이며 원인 체인에 Hikari 연결 확보 시간 초과가 확인됐다.
- 성공 건수와 실제 DB 주문 증가량, 고유 주문번호 수가 일치했다.
- 시험 전용 트리거와 함수는 종료 시 삭제된다. 테스트는 예외 시나리오를 관측하고 DB 정합성을 검증하므로 Gradle의 BUILD SUCCESSFUL이 합성 조건에서 50건 모두 성공했다는 뜻은 아니다.

원인은 `CustomerOrderService.create()`가 `visits.lock()`을 얻은 뒤 주문 처리 전체를 수행하고, `TableVisitService.lock()`이 모든 테이블에 동일한 `pg_advisory_xact_lock(7319021)`을 사용하기 때문이다. 트랜잭션 종료까지 공통 잠금을 유지하므로 서로 다른 테이블 주문도 해당 구간에서는 순서대로 처리된다. 대기 요청도 DB 연결을 점유하여 나머지 요청이 3초 연결 확보 제한에 걸릴 수 있다. 여러 인스턴스가 같은 DB 잠금을 사용하므로 인스턴스 수 증가만으로 이 병목이 사라지지 않는다.

## 권장 후속 조치

1. 주문·방문·병합·이동·결제의 정합성을 유지하면서 공통 잠금을 테이블/방문 단위 잠금으로 축소한다. 여러 테이블을 잠그는 작업은 일관된 잠금 순서를 적용하고 동시성 회귀 시험을 수행한다. 잠금을 단순 삭제하면 안 된다.
2. `NEXT_DISPLAY_NUMBER` 단일 행 잠금도 검토한다. 전역 잠금 제거 후에도 다음 직렬 처리 구간이 될 수 있다.
3. DB 연결 대기 제한과 SSE 전용 DB 연결 분리를 검토한다. pool 크기만 늘리는 것은 공통 잠금에 대기하는 연결을 늘릴 뿐 근본 해결이 아니다.
4. 별도 Cloud Run·DB 테스트 환경에서 운영과 같은 1 vCPU/1GiB로 SSE 50개, 직원 화면, 주문 50건을 함께 검증한다. 한 인스턴스로 시작하는 경우와 미리 확장한 경우를 비교한다. 운영 승인 기준은 주문 실패 0건, 중복·누락 0건과 합의된 p95 응답 시간이다.

./qr-order-backend/gradlew -p qr-order-backend test --tests com.caucse.qrorder.FiftyCustomerCapacityTest --console=plain
