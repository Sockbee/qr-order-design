## 2. #35 — 결제 이후 주문 내역 누적 수정

**이슈 요구사항:** 테이블이 계산한 이후에도 주문 내역이 계속 쌓이는 문제를 수정한다.

### 현재 코드에서 확인한 내용

- [StaffOperationsService.java](../../qr-order-backend/src/main/java/com/caucse/qrorder/domain/StaffOperationsService.java)의 `confirmPayment()`는 청구 그룹의 세션을 `CLOSED`로 종료하고 결제 상태를 `PAID`로 기록한다.
- [CustomerOrderService.java](../../qr-order-backend/src/main/java/com/caucse/qrorder/domain/CustomerOrderService.java)의 `list()`는 주문 목록과 `sessionTotalAmount` 모두 `table_id`만으로 조회한다. 종료된 세션과 과거 방문을 제외하지 않는 경로가 확인된다.
- 같은 서비스의 `openOrCreateSession()`은 열린 세션이 없으면 새 세션을 생성한다. 새 주문 생성뿐 아니라 **조회 범위도 같은 방문 기준으로 맞추는 작업**이 필요하다.

### 해야 할 작업

- [ ] 주문 → 결제 확정 → 같은 테이블 재주문 순서로 고객 내역과 스태프 테이블/결제 화면을 확인한다.
- [ ] 고객 주문 목록·최신 상태·누적 합계를 현재 방문 세션 기준으로 통일한다. 조회만으로 새 세션이 생성되지 않게 한다.
- [ ] 현재 방문이 없으면 빈 목록과 합계 0을 반환하도록 처리한다. 결제 직후 영수증을 유지해야 한다면 현재 주문과 구분하는 정책을 먼저 정한다.
- [ ] 테이블 이동·합석·분리 시 고객 QR이 가리키는 세션과 조회 범위를 점검한다. 단순히 `UNPAID` 조건만 추가해 과거 미결제 이력이 섞이지 않도록 한다.
- [ ] 결제 이벤트 수신·재조회 후 이전 내역이 화면이나 브라우저 저장 상태에서 되살아나는지 확인하고 필요한 갱신 처리를 수정한다.
- [ ] 과거 주문·결제 기록은 보존하고 다음 방문의 주문 목록 및 합계에서 제외한다.

### 완료 기준

- [ ] 방문 A를 결제한 뒤 방문 B가 주문하면 B의 내역·합계에 A가 포함되지 않는다.
- [ ] 새로고침, QR 재진입, 기존 화면의 실시간 갱신에서도 같은 결과가 나온다.
- [ ] 이동·합석·분리 후 결제한 경우에도 방문 간 주문이 섞이지 않는다.
- [ ] 결제와 추가 주문이 겹쳤을 때 종료된 세션에 미결제 주문이 남지 않는지 검증한다.

Figma `staff/TableDetailPanel`(`89:8`)에서 `결제 확인` 버튼을 제거했다. 컴포넌트라서 A02(`90:183`)에 자동 반영된다. 액션 영역이 284→220으로 줄고 그만큼 주문 목록이 310→374로 늘었다.

- [ ] 테이블 상세에는 해당 버튼이 없고, 결제 페이지에서는 정상 결제 및 금액 변경 오류 처리가 동작한다.

## 4. #37 — 테이블 메모와 주문 수정 분리

**이슈 요구사항:** 두 버튼이 같은 화면으로 이동하는 문제를 수정하고, `메모`는 테이블 메모, `주문수정`은 주문 수정으로 동작하게 한다.

### 현재 코드에서 확인한 내용

- [StaffApp.tsx](../../qr-order-frontend/src/StaffApp.tsx)에서 `/note`와 `/edit`는 모두 `StaffTableOperationRoute operation="edit"`를 렌더링한다.
- [StaffOperationRoutes.tsx](../../qr-order-frontend/src/pages/staff/StaffOperationRoutes.tsx)와 [EditOrderPanel.tsx](../../qr-order-frontend/src/components/staff/EditOrderPanel.tsx)는 주문 수량 수정·항목 취소와 메모 편집을 한 화면에서 처리한다.
- [operations.ts](../../qr-order-frontend/src/api/staff/operations.ts)의 `saveStaffTableNote()`는 `orders/update`의 `note` 작업을 호출한다. 서버는 테이블의 최신 비취소 주문에 메모를 저장한다. 주문이 없으면 저장할 수 없고, 최신 주문이 서비스 주문인 경우에도 현재 검증에 걸릴 수 있다.

### 결정 사항 (확정 2026-09-13)

- **메모는 현재 방문 세션에 속한다.** 결제나 초기화로 방문이 끝나면 다음 손님에게 보이지 않는다. 이 수명을 입력칸 바로 아래에 문장으로 표시한다.
- **메모 대상 구분(`general` / `kitchen` / `serving`)을 두지 않는다.** 주방·서빙 지시는 주문 수정 화면과 주방 카드가 담당하므로 테이블 메모는 하나면 충분하다. 그 결과 전용 화면이 아니라 **다이얼로그**로 충분하다.
- 주문이 없는 테이블의 메모 허용 여부는 **저장 위치를 세션으로 옮길 때 함께 정한다.** 현재 서버가 최신 주문에 메모를 붙이는 구조라 이 결정이 API 변경과 묶여 있다.

디자인: `A11 — Table Note`(`326:1800`). A08은 `A08 — Edit Order`로 이름을 바꾸고 메모 블록을 제거해 주문 수정 전용이 됐다.

### 해야 할 작업 및 완료 기준

- [ ] `/note`에 메모 전용 화면을 연결하고 `/edit`는 주문 수량 수정·항목 취소에 집중하도록 분리한다.
- [ ] 결정한 저장 기준에 맞춰 조회·저장 API와 DB 변경 필요 여부를 정리한다. 세션 메모로 바꾼다면 기존 주문 요청사항을 덮어쓰지 않게 한다.
- [ ] 기존 메모 불러오기·저장·삭제(빈 값 저장)·저장 실패·닫기 동작을 구현하고 검증한다.
- [ ] 추가 주문이 생겨도 현재 방문의 테이블 메모가 유실되거나 다른 주문 메모로 바뀌지 않는다.
- [ ] 메모 버튼은 메모 전용 화면, 주문 수정 버튼은 주문 편집 화면을 열며 각각의 변경이 다른 데이터에 영향을 주지 않는다.
- [ ] 결제·초기화 이후 메모 처리와 이동·합석·분리 시 메모 표시가 확정한 정책과 일치한다.

## 5. #40 — 테이블 초기화 기능

**이슈 요구사항:** 주문이나 정산이 꼬였을 때 테이블을 완전히 초기화할 수 있어야 한다.

본문은 초기화의 데이터 범위를 정의하지 않는다. 아래 표의 **권장 방향을 그대로 확정했다(2026-09-13).** 디자인은 `A12 — Table Reset`(`327:1933`)이며, 확인 다이얼로그가 `초기화 대상`(합석 그룹·미결제 금액)과 `이렇게 됩니다` 박스로 이 정책을 문장으로 서술한다. 진입점은 A02 액션 영역의 독립 행(danger 아웃라인)이다 — `주문 취소` 옆에 두지 않은 이유는 danger 두 개가 인접하면 오클릭 위험이 크고, 초기화는 방문 자체를 끝내는 다른 성격의 행위이기 때문이다.

### 결정 사항 (확정 2026-09-13 — 아래 권장 방향대로)

| 항목 | 쟁점 | 확정 정책 |
| --- | --- | --- |
| 주문·결제 이력 | 삭제할지, 보존하고 현재 방문에서 제외할지 | 기록을 보존하고 방문을 종료한다. 초기화 자체가 결제 완료나 환불을 뜻하지 않게 한다. |
| 미결제·미완료 주문 | 취소·면제·복구 중 어떤 상태로 남길지 | 정상 결제와 구분되는 처리 규칙을 정하고 사유를 기록한다. |
| 합석·이동 | 선택 테이블만 또는 청구 그룹 전체를 초기화할지 | 영향을 받는 테이블을 먼저 보여주고, 지원하지 않는 상태는 명확히 거부한다. |
| 호출·할인·메모 | 다음 방문으로 이어질 정보가 있는지 | 현재 방문에 속한 값은 다음 방문에서 제외한다. |
| 서비스 주문·스태프 정산 | 서비스 주문 및 개인 부담액도 취소할지 | 고객 테이블 복구가 스태프 정산 금액을 임의로 바꾸지 않도록 별도로 정의한다. |
| QR·테이블 설정 | 토큰, 표시명, 활성 상태도 초기화할지 | 기본적으로 유지하여 기존 QR을 계속 사용할 수 있게 한다. |

### 해야 할 작업

- [ ] #35의 세션 종료·조회 범위를 재사용하고 #37의 메모 정책을 반영한 초기화 계약을 작성한다.
- [ ] 스태프 전용 초기화 API를 추가한다. 현재 세션 식별·검증, 트랜잭션과 잠금, 중복 요청 처리를 포함한다.
- [ ] 첫 초기화 이후 새 방문이 시작됐을 때 이전 요청을 재전송해도 새 방문이 초기화되지 않도록 보호한다.
- [ ] 테이블 상세에 초기화 진입점을 만들고, 대상 테이블·영향 범위·미결제 금액을 보여주는 확인 화면을 제공한다.
- [ ] 실행 스태프·시각·대상 세션·처리 결과·사유를 기록한다.
- [ ] 확정한 정책에 따라 주문·호출·할인·메모·합석 관계를 처리하고, 고객 및 운영 화면 갱신 이벤트를 발행한다.

### 완료 기준

- [ ] 초기화 후 테이블은 새 방문의 주문을 받을 수 있고 이전 방문 정보가 새 주문에 섞이지 않는다.
- [ ] 고객 내역, 테이블 상세, 주방·서빙·결제 대기열에 처리 전 상태가 남지 않는다.
- [ ] 빈 테이블, 합석 테이블, 서비스 주문 포함 테이블을 정책에 맞게 처리한다.
- [ ] 중복 클릭·타임아웃 후 재시도·동시 주문·동시 결제에서 부분 초기화나 새 방문 초기화가 발생하지 않는다.
- [ ] 고객 권한으로 실행할 수 없고, 과거 거래 및 복구 작업 기록을 확인할 수 있다.

## 6. #36 — 메뉴별 조리 완료 체크

**이슈 요구사항:** 메뉴별로 조리 완료를 체크할 수 있어야 한다. 본문에 처리 단위나 상세 동작은 명시되어 있지 않다.

### 현재 코드에서 확인한 내용

- [StaffStationRoutes.tsx](../../qr-order-frontend/src/pages/staff/StaffStationRoutes.tsx)의 조리 완료 버튼은 `orderId`로 주문 전체를 `ready`로 바꾼다.
- [StationOrderCard.tsx](../../qr-order-frontend/src/components/staff/StationOrderCard.tsx)는 메뉴명·수량을 표시하지만 항목별 체크는 제공하지 않는다.
- 서버의 `updateStatus()`도 테이블 또는 주문 단위로 상태를 변경한다. 주문 항목의 기존 `ACTIVE` / `CANCELLED`는 취소 여부이므로 조리 상태와 구분해야 한다.

### 결정 사항 (확정 2026-09-13)

- **체크 단위는 주문 항목 한 줄이다.** 수량별 완료는 다루지 않는다.
- **완료된 항목부터 서빙 대기열로 내보낸다.** 주문의 모든 항목이 끝날 때까지 기다리지 않는다. 그 결과 서빙 대기열은 주문 단위가 아니라 항목 묶음 단위가 되며, B02 카드도 함께 바뀐다.
- **주문 전체 완료 버튼은 유지하되 `전체 완료`로 바꾼다.** 남은 항목을 한 번에 체크하는 보조 수단이며, 주된 동작은 항목별 체크다.
- 취소된 항목은 완료 판정에서 제외한다.
- 완료 체크 취소와 완료 후 수량 변경 허용 여부는 **항목 상태 필드를 설계할 때 함께 정한다.**

디자인: `staff/KitchenOrderCard`(`88:68`) 세 variant 전부에 항목 체크박스·`조리 n/m` 칩·`전체 완료` 버튼을 넣었고, `staff/ServingOrderCard`(`88:126`)에는 `일부 · 주방 n개` 칩을 넣어 같은 주문에 아직 조리 중인 항목이 있음을 알린다.

### 해야 할 작업 및 완료 기준

- [ ] 항목별 조리 상태 저장 필드와 기존 데이터의 초기값을 정의하고 Flyway 마이그레이션을 작성한다.
- [ ] 항목 ID로 상태를 변경하는 운영 API와 응답 타입을 추가한다. 같은 메뉴라도 다른 주문·옵션 항목의 체크가 함께 바뀌지 않게 한다.
- [ ] 주방 카드에 완료/미완료·처리 중·실패 상태를 표시하고 재조회 후에도 체크를 유지한다.
- [ ] 항목 상태에서 주문 상태를 계산하는 규칙을 구현한다. 취소 항목은 완료 판정 대상에서 제외한다.
- [ ] 주방·서빙·테이블 상세·고객 주문 상태가 확정한 부분 완료 정책과 일치하도록 연결한다.
- [ ] 서로 다른 메뉴가 포함된 주문에서 한 메뉴의 체크가 다른 메뉴를 완료 처리하지 않는다.
- [ ] 동일 메뉴의 서로 다른 옵션, 여러 수량, 항목 취소, 완료 후 수정, 두 기기의 동시 체크를 검증한다.

## 7. 작업 시 공통 검증과 종료 조건

- API·상태 변경은 [QrOrderApiIntegrationTest.java](../../qr-order-backend/src/test/java/com/caucse/qrorder/QrOrderApiIntegrationTest.java)의 기존 시나리오를 참고해 회귀 검증한다. #35의 세션 경계, #40의 재시도·동시 처리, #36의 항목 상태 전이는 통합 테스트로 확인한다.
- UI 변경은 실제 스태프 화면에서 버튼 진입·저장·실패·재조회 흐름을 확인한다. API 모드와 개발용 목 데이터가 다르게 동작하지 않는지도 확인한다.
- 코드 변경 시 관련 테스트와 프론트엔드 lint/build를 실행한다. 이 문서 작성 단계에서는 제품 코드나 실행 결과를 변경하지 않는다.
- 각 이슈는 구현뿐 아니라 위 완료 기준을 확인한 뒤, 변경 파일·검증 결과·남은 제약을 정리해 종료 여부를 판단한다.

이 문서는 확인일 기준의 작업 목록이다. 착수 시 GitHub의 최신 본문·댓글·상태를 다시 확인하고, 결정한 정책과 완료 체크를 갱신한다.
