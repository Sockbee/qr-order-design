## 2. 좌측 레일

`staff/StaffNavigation` (`84:90`, 페이지 `Staff / Controls & Feedback`)

항목 7개, 순서 고정:

```text
테이블 · 주방 · 서빙 · 결제 · 서비스 · 품절 · 설정
```

- `설정`은 주 워크플로 바깥이므로 **항상 마지막**이다.
- variant는 `Active` 하나이며 값은 `Tables` / `Kitchen` / `Serving` / `Payment` /
  `Service` / `SoldOut` / `Settings` 7개다.
- 활성 항목만 배경 `bg/weak` + 라벨 `text/weak`, 나머지는 배경 없음 + `text/body`.
- 배지 정책:
  - `테이블` — 주의가 필요한 테이블 수(호출 + 지연). 빨간 주의 배지이며 **어느 화면에
    있든 참이므로 `Active`와 무관하게 유지**한다.
  - `주방` / `서빙` / `결제` — 각 대기열 건수.
  - `서비스` — 미정산 **인원 수**. 지급 건수가 아니다. 총무가 밤 끝에 0으로 만들어야
    하는 숫자가 인원 수이기 때문이다.
  - `품절` / `설정` — 배지 없음. 품절 수를 배지로 띄우려면 모든 화면이 카탈로그를 읽어야
    하는데 그런 화면이 없어 자기 화면에서만 보이는 숫자가 된다.

Staff POS 페이지의 모든 프레임은 이 컴포넌트의 **인스턴스**를 쓴다. 로컬로 그린 레일은
없다. 레일을 바꾸려면 `84:90` 한 곳만 고친다.

코드 쪽 단일 정의는 `src/components/staff/staffNavItems.ts`다.

## 3. 화면별 정책

### 3.1 A02 — 테이블 상세

액션 배치(위에서 아래):

```text
서비스 제공        (주 버튼, 파란 채움)
이동 · 합석 · 분리 · 할인
메모 · 주문 수정 · 주문 취소
테이블 초기화       (독립 행, danger 아웃라인)
```

- **주 버튼은 `서비스 제공`이다.** A02에서만 할 수 있는 일이기 때문이다. 익숙한 자리라
  잘못 눌릴 수 있지만 A10에 들어가는 것만으로는 아무것도 기록되지 않는다 — 부담 스태프를
  고르고 확인 다이얼로그를 읽어야 주문이 쓰인다.
- **`결제 확인` 버튼은 없다(이슈 #38).** B03 결제 페이지와 중복이며, 결제 확정은 B03
  에서만 한다.
- **`테이블 초기화`는 `주문 취소` 옆 4번째 슬롯이 아니라 독립 행에 둔다(이슈 #40).**
  danger 두 개가 붙으면 오클릭 위험이 크고, 초기화는 주문 하나를 무르는 것이 아니라
  방문 자체를 끝내는 다른 성격의 행위다.

### 3.2 A11 — 테이블 메모 (이슈 #37)

`메모`와 `주문 수정`은 서로 다른 화면을 연다. 이전에는 둘 다 A08로 갔다.

- 메모는 **다이얼로그**다. 전체 화면이 아니다.
- **대상 구분(`general` / `kitchen` / `serving`)을 두지 않는다.** 주방·서빙 지시는 이미
  주문 수정 화면과 주방 카드가 담당하므로, 테이블 메모는 "이 팀에 대한 메모" 하나로
  충분하다.
- **메모는 현재 방문 세션에 속한다.** 결제나 초기화로 방문이 끝나면 다음 손님에게
  보이지 않는다. 이 수명을 입력칸 바로 아래에 문장으로 적는다 — 정책은 읽는 자리에
  있어야 지켜진다.
- 추가 주문이 생겨도 현재 방문의 메모는 유실되거나 다른 주문의 메모로 바뀌지 않는다.

### 3.3 A12 — 테이블 초기화 (이슈 #40)

주문이나 정산이 꼬였을 때 테이블을 비우는 복구 동작이다. 확인 다이얼로그는 대상과 영향
범위를 먼저 보여준 뒤 확정을 받는다.

| 항목 | 정책 |
|---|---|
| 주문·결제 이력 | **보존**한다. 방문만 종료하며 초기화가 결제나 환불을 뜻하지 않는다 |
| 미결제·미완료 주문 | 취소로 기록하고 사유를 남긴다. 정상 결제와 구분한다 |
| 합석·이동 | 영향받는 테이블을 먼저 보여준다. 지원하지 않는 상태는 명확히 거부한다 |
| 호출·할인·메모 | 현재 방문에 속한 값이므로 함께 종료한다 |
| 서비스 주문·스태프 정산 | **바꾸지 않는다.** 고객 테이블 복구가 개인 부담액을 임의로 변경하면 안 된다 |
| QR·표시명·활성 상태 | 유지한다. 기존 QR을 계속 쓸 수 있어야 한다 |

다이얼로그는 `초기화 대상`(합석 그룹과 미결제 금액)과 `이렇게 됩니다` 박스로 위 정책을
문장으로 서술한다. 확정 버튼은 danger다.

### 3.4 B01 / B02 — 항목별 조리 완료 (이슈 #36)

- **체크 단위는 주문 항목 한 줄**이다. 같은 메뉴 3개 중 1개 같은 수량별 완료는 다루지
  않는다.
- **완료된 항목부터 서빙 대기열로 내보낸다.** 주문의 모든 항목이 끝날 때까지 기다리지
  않는다.
- 주방 카드(`staff/KitchenOrderCard`, `88:68`)
  - 항목마다 체크박스. 완료한 항목은 취소선 + 뮤트 처리로 카드에 남아, 무엇이 이미
    나갔는지 보인다.
  - 헤더에 `조리 n/m` 진행 칩.
  - 하단 버튼은 `조리 완료`가 아니라 **`전체 완료`** — 남은 항목을 한 번에 체크하는
    단축이다. 항목 체크가 주된 동작이고 이쪽이 보조다.
  - 취소된 항목은 완료 판정에서 제외한다.
- 서빙 카드(`staff/ServingOrderCard`, `88:126`)
  - `Items`에는 나갈 준비가 된 항목만 들어간다.
  - 같은 주문에 아직 조리 중인 항목이 있으면 헤더 칩이 `일부 · 주방 n개`로 남은 수를
    함께 말한다. 서빙 담당이 "이게 주문 전부인가"를 묻지 않아도 되게 한다.
  - 이 정보를 별도 줄이 아니라 칩에 넣은 이유는 카드 높이 320px을 지키기 위해서다.
    353px이 되면 B02가 두 번째 행을 담지 못하고 잘린다.

### 3.5 B05 — 품절 관리

- `품절` / `판매 중` 두 섹션. 스위치를 누르면 카드가 반대편 섹션으로 옮겨간다.
- **확인 단계가 없다.** 한 번 탭으로 전환되고, 되돌리는 것도 한 번이다. 재고 관리
  제품이 아니라 "없는 음식이 주문되지 않게 막는" 한 가지 일만 한다.
- 헤더가 `품절 n · 판매 중 m`을 보여준다.
- 운영 설정(`/staff/settings`)에도 메뉴별 `판매` 체크박스가 있다. **의도한 중복**이다 —
  설정은 이름·가격을 같이 고치는 관리자 폼이라 행마다 저장을 눌러야 하고, B05는 서비스
  중 서서 한 번 탭하는 용도라 필요한 상호작용이 다르다. 합치면 둘 중 하나가 나빠진다.
- 단, **옵션 단위 품절은 설정에만 있다.** B05는 메뉴 단위만 다룬다.
- 카탈로그 소스는 A10과 같은 `useStaffMenu`라 두 화면이 품절 상태를 두고 어긋나지 않는다.

### 3.6 A10 / B04 — 서비스 지급과 정산

지급·부담금 계약은 `google-sheets-schema.md` §9/§19와
`apps-script-api-design.md` §4.20~§4.22에 있다. 화면 쪽 정책만 여기 적는다.

- A10은 다이얼로그가 아니라 전체 화면이다. 메뉴 그리드가 필요하고, 부담 스태프(필수)와
  손님 메시지(선택)라는 결정이 둘 더 붙는다.
- **A10에는 확인 다이얼로그가 있다.** 명단의 특정 개인에게 금액을 지우는 행위이고 지급
  후에는 수정할 수 없기 때문이다. 다이얼로그는 손님에게 보낼 메시지를 인용해 되보여준다.
- 손님 메시지는 내부 사유 메모가 아니라 **손님 화면에 그대로 뜨는 문장**이다. 입력칸
  아래에 그 사실을 적는다.
- B04 미정산 섹션은 **부담액이 있는 인원만** 보여주고 금액 내림차순으로 정렬한다. API는
  명단 전체를 반환하지만 지급 이력이 없는 사람은 낼 것이 없고, ₩0 카드가 실제로 찾아가야
  할 사람을 덮는다.

## 4. 시각 언어

`A00 — Staff Foundations`(`98:1403`)가 원본이다. 여기 적는 것은 이번 화면들이 실제로
따른 값이다.

| 값 | 크기 |
|---|---|
| 뷰포트 | 1194 × 834 (아이패드 가로 고정) |
| 레일 | 88 |
| 헤더 | 72 |
| 본문 거터 | 24 |
| 우측 인스펙터/작업 패널 | 420 |
| 대기열 카드 | 342 × (내용에 따름, 서빙 카드는 320 고정) |
| 운영 버튼 높이 | 56 (고객 앱 48보다 큼 — 서서, 팔 길이에서 조작) |
| 다이얼로그 | wide 680 / narrow 480, 라운드 16 |

- 다이얼로그는 `Backdrop + Scrim + Dialog` 구조이며 A04~A07이 원형이다. 새 다이얼로그는
  이 프레임을 복제해 본문만 바꾼다. **새 셸을 만들지 않는다.**
- 모든 다이얼로그는 확정 버튼 앞에 결과를 문장으로 서술한다(`이렇게 됩니다` 박스). 드물고
  되돌리기 어려운 동작일수록 동사만 보고 짐작하지 않게 한다.
- danger는 채움이 아니라 아웃라인이다. `#e42939`는 실패와 지연 전용이다.
- 그림자를 쓰지 않는다. 분리는 구분선·스크림·여백으로만 한다.

### 색 변수 모드 — 주의

`Color` 컬렉션에 모드가 **둘** 있다.

| 모드 | 용도 |
|---|---|
| `Light` (기본값) | 고객 앱 웜/한옥 팔레트 |
| `Staff` (`189:0`) | 운영 앱 블루 팔레트 |

기본 모드가 `Light`이므로, 플러그인 API로 변수 값을 읽어 색을 칠할 때 모드를 지정하지
않으면 **고객용 살구색이 칠해진다.** 스태프 컴포넌트를 코드로 만질 때는 `Staff` 모드로
해석하고, 컴포넌트에 `setExplicitVariableModeForCollection`으로 모드를 명시한다.
`staff/StaffNavigation`은 이 처리가 되어 있다.

## 6. Figma와 코드의 차이

**현재 Figma가 코드보다 앞서 있다.** 아래는 디자인만 있고 구현되지 않은 상태다.

- A02에 `결제 확인` 버튼이 **코드에는 아직 있다**(`TableDetailPanel.tsx`).
- A02에 `테이블 초기화` 버튼이 **코드에는 없다.** 초기화 API도 없다.
- `/staff/tables/:tableId/note`가 **코드에서는 여전히 주문 수정 화면을 연다.** A11에
  해당하는 메모 전용 화면이 없다.
- 주방·서빙 카드에 **항목별 조리 상태가 없다.** 조리 완료는 여전히 주문 단위다. 항목별
  상태 필드와 마이그레이션도 없다.

구현할 때는 이 문서의 정책과 [open-issues-action-plan.md](./open-issues-action-plan.md)의
완료 기준을 함께 확인한다.
