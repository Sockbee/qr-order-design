# 예약 입장 시 동시 주문 안정화 이슈

작성일: 2026-09-16 (KST)

상태: 코드 구현·로컬 검증 완료 / 운영 반영·용량 검증 대기

대상: 최대 100석 매장, 20시 예약 손님 약 40명이 각자 휴대전화로 주문하는 상황

목표는 예약 손님이 몰려도 주문이 실패하거나 중복되지 않고, 직원 화면의 주문·조리·서빙·결제 상태가 일관되게 유지되는 것이다. 아래 번호는 문서 내 작업 ID이며 GitHub 이슈 번호가 아니다. 수치와 동작 중 **제안**으로 표시한 항목은 구현·검증을 위한 초안이다.

## 구현 진행 상황 (2026-09-16)

[구현·검증 기록 및 예약 운영 절차](reservation-capacity-implementation.md)에 잠금 설계, DB 연결 예산, 테스트 결과와 남은 배포 조건을 정리했다. CAP-01의 고객·직원·서비스 **주문 생성**은 테이블/그룹 단위로 병렬화했으며, 직원 구조 변경은 공통 배타 잠금을 유지했다. CAP-02는 변수화·수동 준비/복원 도구, CAP-03은 메뉴 화면 5분 유휴 중지를 구현했다.

아래 체크는 실제 끝낸 범위만 표시한다. 운영 결과가 필요한 완료 기준은 체크하지 않는다. 현재 브랜치는 운영 배포보다 이전 기능을 포함하므로 직접 배포하지 않았다.

## 근거와 현재 상태

[운영 API·DB 부하 시험](../production-capacity-test-2026-09-16.md)에서 고객 SSE를 유지한 채 각 고객이 주문 1건과 조회 1건을 동시에 요청했다.

| 동시 고객 | 주문 성공 | 주문 p95 | 조회 성공 | 조회 최대 |
|---:|---:|---:|---:|---:|
| 10명 | 10/10 | 1.30초 | 10/10 | 0.45초 |
| 30명 | 30/30 | 3.55초 | 30/30 | 2.76초 |
| 50명 | 45/50 | 4.85초 | 46/50 | 36.49초 |

- 실패 9건은 Hikari DB 연결 확보 제한 3초를 초과한 HTTP 500이었다.
- 주문 경로는 테이블이 달라도 공통 트랜잭션 잠금 `pg_advisory_xact_lock(7319021)`을 사용한다. 코드와 실패 로그상 우선 조사·개선 대상이며, 운영 시험에서 개별 잠금 대기 시간을 직접 측정하지는 않았다.
- 추가 Cloud Run 인스턴스 준비에는 약 26~36초가 걸렸다. DB 잠금·연결 대기와 서버 확장 대기를 구분해 개선해야 한다.
- 현재 설정은 인스턴스당 동시 요청 100개, 최소 1개, 최대 5개, 1 vCPU / 1GiB다. 최대 동시 HTTP 요청 용량 500은 500건의 주문 처리 성능 보장이 아니다.
- SSE는 최대 25분 유지되고 클라이언트가 약 24분에 연결을 교체한다. 종료 후 자동 재접속이 있으며, 화면이 숨겨지면 클라이언트 연결과 자동 조회를 중지하는 처리는 이미 있다.
- 실시간 HTTP 연결과 DB 연결 풀은 별개다. 미사용 SSE를 줄여도 활동 중인 예약 손님의 주문 트랜잭션 병목은 남는다.

## CAP-01 — 공통 DB 잠금과 연결 풀 대기로 인한 동시 주문 실패 개선

### 문제와 기대 동작

여러 테이블의 주문이 같은 잠금을 기다리는 동안 DB 연결이 점유되어, 새 주문과 조회가 3초 내에 연결을 얻지 못한다. 서로 독립적인 테이블의 주문은 병렬 처리하고, 같은 방문이나 청구 그룹을 변경하는 작업만 필요한 범위에서 순서를 보장해야 한다.

### 작업 범위

- [ ] 주문 생성부터 커밋까지의 잠금 획득 순서, 잠금 유지 시간, SQL 실행 횟수와 DB 연결 대기를 측정한다. 고객 주문·직원 주문·서비스 주문·조리 변경·테이블 병합/분리/이동·결제·초기화·메뉴 변경 경로를 함께 조사한다.
- [ ] 공통 잠금을 테이블/방문/청구 그룹 단위로 축소하는 설계를 작성한다. 아직 세션이 없는 첫 주문도 보호하고, 이동·합석으로 원본 QR과 현재 테이블이 달라지는 경우를 포함한다.
- [ ] 여러 테이블/세션이 필요한 작업에는 일관된 잠금 순서를 적용한다. 잠금 대기 중 그룹 구성이 바뀐 경우 대상과 버전을 다시 검증한다. 주문 생성의 잠금만 제거하고 다른 변경 경로는 그대로 두지 않는다.
- [x] `NEXT_DISPLAY_NUMBER` 단일 행 잠금과 번호 할당 시점을 검토한다. PostgreSQL sequence 등을 검토할 경우 번호 유일성, 표시 형식, 롤백 시 번호 누락 허용 정책을 명시한다.
- [x] 동일 `clientRequestId`의 동시 재전송이 주문 한 건만 만들도록 보장한다. 기존 요청과 다른 내용의 재사용은 충돌로 처리하고, 첫 방문 세션이 중복 생성되지 않게 한다.
- [x] PostgreSQL 이벤트 리스너의 장기 연결을 일반 요청용 풀에서 분리할 필요를 평가한다. 실제 DB `max_connections`와 기존 연결을 조회하고, 최대 인스턴스 수 × 각 풀 크기 + 리스너 + 운영 여유를 포함해 연결 예산을 계산한다.
- [x] 풀 크기·연결 확보 제한·잠금 제한은 측정 결과에 따라 조정한다. 단순히 3초를 늘리거나 풀 크기를 키우는 것만으로 완료 처리하지 않는다.
- [x] DB 연결 확보 실패를 식별 가능한 재시도 가능 오류로 구분한다. 재시도를 도입한다면 동일 요청 ID, 제한 횟수, 지연·분산을 적용하고 원래 요청의 커밋 여부를 확인한다. 오류를 감추는 무제한 재시도는 넣지 않는다.

### 완료 기준

- [ ] 서로 다른 40개·50개 테이블 주문에서 DB 연결 확보 실패가 재현되지 않는다. 같은 테이블/방문에 몰리는 주문도 데이터가 일관된다.
- [ ] 중복 요청으로 주문·방문·결제·서비스 정산이 중복 생성되지 않는다.
- [ ] 주문과 결제/초기화/병합/이동/조리 변경이 겹쳐도 금액·세션·항목 상태가 맞고 교착상태가 없다.
- [ ] 롤백된 주문의 이벤트가 고객·직원 화면에 전달되지 않으며, 커밋된 주문의 이벤트가 전달된다.
- [ ] 개선 전후 연결 대기, 잠금 대기, p95·최대 응답 시간, 오류 수를 같은 시나리오로 비교한 결과를 첨부한다.
- [ ] 아래 통합 부하 검증과 관련 정합성 회귀 시험을 통과한다.

## CAP-02 — 예약 입장 전에 Cloud Run 처리 인스턴스 준비

### 문제와 기대 동작

최대 인스턴스를 5개로 설정해도 평소 실행 중인 인스턴스는 1개일 수 있다. 손님이 몰린 뒤 확장을 시작하면 준비에 수십 초가 걸린다. 예약 시간 전에 필요한 용량을 확보하고 피크 종료 후 평소 설정으로 복원할 수 있어야 한다.

### 작업 범위

- [x] `infra/main.tf`의 서비스 최소·최대 인스턴스와 리비전 최대 인스턴스, 동시 요청 설정을 변수화하고 기본값·적용 범위를 문서화한다. 서비스와 리비전 제한이 서로를 막지 않게 한다.
- [ ] **제안:** 최소 2개·3개를 비교 시험해 필요한 준비 수량을 정한다. 최소 3개가 충분하다고 미리 단정하지 않으며 DB 연결 예산과 함께 결정한다.
- [ ] **제안 운영 절차:** 20시 예약이면 19:50에 피크 설정을 적용하고 19:55까지 준비 상태를 확인한다. 이는 절차 예시이며 현재 예약된 자동화가 아니다. 날짜·반복 요일·종료 시각은 실제 영업 일정에 맞춰 지정한다.
- [ ] 서비스 전체 `Ready` 외에 준비된 인스턴스 수와 DB 연결 상태를 확인한다. 단일 health 요청으로 모든 인스턴스의 준비 완료를 판단하지 않는다.
- [x] 피크 설정 적용·확인 실패 시 재시도 범위, 담당자 확인 절차, 정상 설정 복원 절차를 작성한다. 이전 값을 기록하고 복원 실패를 드러내도록 한다.
- [ ] 자동화를 도입하는 경우 `Asia/Seoul` 기준 일정, 수동 실행, 중복 실행 방지와 배포 중 충돌 처리를 포함한다. 인프라 코드와 실제 운영 설정이 장기간 어긋나지 않게 한다.
- [ ] 추가 실행 시간에 따른 비용과 DB 연결 수 변화를 비교 결과에 기록한다.

### 완료 기준

- [ ] 예약 시점에 검증된 수량의 인스턴스가 준비되어 있고, 첫 주문부터 목표 응답 시간을 충족한다.
- [ ] 평소 최소 1개에서 시작한 시험과 사전 준비한 시험의 오류·지연을 비교한다.
- [ ] 피크 종료 후 이전 최소 인스턴스 설정을 복원하고, 새 배포에도 동시 요청·최대 인스턴스 설정이 유지된다.
- [ ] CAP-01과 결합한 40명·50명 주문 검증을 통과한다. 인스턴스 증설만으로 DB 잠금 이슈를 완료 처리하지 않는다.

## CAP-03 — 미사용 고객 화면의 실시간 연결·자동 조회 일시 중지

### 문제와 기대 동작

메뉴만 열어 둔 화면도 SSE 연결과 조회를 유지한다. 연결 제한 시간만 짧게 바꾸면 자동 재접속이 반복되어 부하가 줄지 않을 수 있다. 미사용 상태에서는 연결·조회·재접속을 함께 멈추고, 사용자가 돌아오면 최신 상태를 복구해야 한다.

### 제안 동작

| 상황 | 동작 |
|---|---|
| 메뉴 화면에서 사용자 조작 없이 5분 경과 | 고객 SSE, 정기 조회, 예약된 재접속을 일시 중지 |
| 주문 진행 화면 또는 주문 제출·결과 확인 중 | 유휴 타이머 때문에 주문 요청이나 실시간 갱신을 중단하지 않음 |
| 다른 앱/탭으로 이동해 화면이 숨겨짐 | 기존 연결·조회 중지 정책 유지. 전송된 주문의 결과는 복귀 후 같은 요청 ID로 확인 |
| 일시 중지 후 터치·키 입력·화면 복귀 | 최신 메뉴·주문 상태 조회 후 필요한 실시간 연결 재개 |
| 직원 화면 | 고객용 유휴 중지 정책에서 제외 |

5분은 제안 기본값이며 설정 가능하게 한다. 카트·QR 인증 정보·방문 세션은 유휴 타이머로 삭제하지 않는다. 오래된 가격이나 영업 상태로 주문하지 않도록 복귀 시 갱신과 서버의 가격 검증을 유지한다.

### 작업 범위

- [ ] 고객 화면의 상태를 사용 중 / 숨김 / 유휴 중지 / 주문 전송·확인 중으로 구분하고 재접속·조회 타이머의 소유권을 정리한다.
- [x] 터치·키 입력·사용자 스크롤 등 실제 조작을 기준으로 유휴 시간을 계산한다. heartbeat, 서버 이벤트, 렌더링, 자동 조회로 유휴 시간이 초기화되지 않게 한다.
- [x] 의도적인 유휴 중지와 네트워크 오류를 구분한다. 중지 중에는 fallback 조회와 재접속도 멈추고, 네트워크 오류 때의 복구 동작은 유지한다.
- [x] 복귀 시 중복 SSE·중복 조회 루프가 생기지 않게 한다. 여러 사용자의 복귀/재접속에는 작은 시간 분산을 적용하되 실제 주문 전송을 임의로 지연시키지 않는다.
- [ ] 사용자는 다시 화면을 조작하는 것만으로 계속 주문할 수 있게 한다. 최신 정보 로딩 중 상태를 표시하고, 주문 버튼 연타로 중복 주문이 생성되지 않게 한다.
- [ ] 클라이언트 `abort()` 호출뿐 아니라 서버의 SSE 등록 수와 연결 지표 감소도 확인한다. 끊긴 연결이 오래 남으면 서버 정리 경로와 최대 유지 시간, 중복 구독 방지를 함께 검토한다.

### 완료 기준

- [x] 제안된 5분 유휴 이후 고객 화면의 SSE·정기 조회·자동 재접속이 중지된다.
- [x] 주문 진행 화면과 주문 제출·결과 확인 중에는 타이머 때문에 상태 추적이 끊기지 않는다.
- [ ] 복귀 후 메뉴 가격·품절·영업 상태·주문/결제 상태가 최신으로 반영되고 카트가 보존된다.
- [x] 숨김/복귀, 유휴/활동, 페이지 이동을 반복해도 고객당 중복 연결이나 타이머가 누적되지 않는다.
- [x] 직원 화면은 정상적으로 갱신되고, 고객 유휴 정책 변경으로 영향을 받지 않는다.
- [ ] 100개 고객 화면을 열어 둔 뒤 일부를 유휴 상태로 만들었을 때 연결 수와 조회량 감소를 측정한다. 활동 중인 40명의 주문 안정성은 CAP-01·02로 별도 검증한다.

## 통합 검증과 운영 완료 조건

성능 숫자는 아래를 **제안 목표**로 삼아 작업 시작 시 확정한다. 로컬 테스트 통과만으로 운영 완료 처리하지 않는다.

| 시나리오 | 검증 내용 | 제안 목표 |
|---|---|---|
| 예약 입장 | 기존 고객 60명 + 신규 고객 40명으로 총 100개 고객 화면, 직원 화면 4개, 신규 고객 40명 동시 주문·조회 | 주문 오류·중복·누락 0건, 주문 p95 ≤ 2초, 최대 ≤ 5초 |
| 순간 부하 여유 | 총 100개 고객 화면과 직원 화면 4개를 유지한 상태에서 그중 50명이 동시 주문·조회 | 같은 주문 목표, 조회 p95 ≤ 2초, 429/5xx 0건 |
| 평상시 지속 부하 | 위 화면 수에서 5~10건 주문이 10초마다 들어오는 조건을 10분 실행 | 오류·중복·누락 0건, DB 연결 대기·SSE 연결 수가 누적 증가하지 않음 |
| 일시 중지·복귀 | 고객 일부 유휴/숨김 전환 후 40명이 복귀 | 갱신 누락·중복 연결 없음, 복귀 집중으로 주문 오류가 생기지 않음 |
| 데이터 경합 | 같은 테이블 주문·재전송과 결제/초기화/병합/이동/조리 변경을 겹쳐 실행 | 금액·세션·주문번호·조리/서빙 단위 정합성 유지, 교착상태 없음 |

- [ ] 고객 100명 수에는 주문하는 40명/50명이 포함됨을 부하 도구에 명시한다. 화면 수, SSE 연결 수, 순간 HTTP 요청 수, 초당 주문 수를 각각 기록한다.
- [ ] 주문 시나리오는 다른 테이블과 같은 테이블의 여러 휴대전화를 모두 포함한다. 기존 시험처럼 명시적인 조회만 보내는 것에 더해 이벤트 수신 후 직원 화면의 재조회도 재현한다.
- [ ] 예약 입장과 50명 순간 부하는 각각 최소 3회 반복한다. 준비된 인스턴스 조건과 최소 1개에서 확장하는 조건을 구분해 기록한다.
- [ ] 운영과 같은 사양의 격리 환경에서 먼저 수행한다. 특히 지속 부하 시험을 기존 운영 스크립트에 그대로 추가해 실행하지 않는다. 운영 재검증은 실행 구간·최대 주문 수·기존 거래 영향·정리 범위를 정한 별도 실행으로 진행한다.
- [ ] 운영 부하 시험은 오류/지연 중단 기준, 전용 데이터 식별, 미완료 요청 확인, 정리 후 잔존 데이터 검사와 결과 보고를 포함한다. 주문번호·이벤트 시퀀스는 기존 거래와 충돌하지 않도록 되돌리지 않는다.
- [ ] Hikari active/idle/pending·연결 timeout, PostgreSQL 잠금 대기, Cloud Run 인스턴스 수·시작 시간·요청 지연, SSE 수를 함께 수집한다. `UP`만으로 정상 판정하지 않는다.
- [ ] 운영 재검증 결과와 실제 반영된 리비전·인프라 설정을 기록하고, 변경별 복원 절차를 확인한 뒤 완료 처리한다.
