# 예약 시간대 동시 주문과 DB 연결 병목 개선

운영에서 50명이 동시에 주문·조회했을 때 주문 5건과 조회 4건이 실패했다. 독립된 테이블 주문까지 공통 잠금으로 직렬화되고, 주문번호 할당과 직원 화면의 중첩 조회가 DB 연결을 오래 점유했다. 이번 변경은 주문 잠금과 연결 사용을 개선하고, 예약 전 인스턴스 준비·복원 도구와 고객 메뉴 화면의 유휴 연결 중지를 추가한다.

- 병합: `fix/reservation-capacity` → `dev`
- 우선순위: CAP-01 주문·DB 병목 → CAP-02 예약 전 준비 → CAP-03 유휴 연결
- `origin/dev`의 `7aaa673`까지 통합했다. 운영 배포와 변경 후 운영 부하 재검증은 별도 진행해야 한다.

## 주요 변경

### 동시 주문과 직원 조회

- 고객·직원·서비스 주문은 테이블과 청구 그룹 단위로 보호해 서로 독립된 주문을 동시에 처리한다. 같은 테이블의 첫 방문, 중복 요청, 합석 그룹과 이동 전 QR의 일관성은 유지한다.
- 결제·초기화·이동·합석·분리·조리 상태 변경 등은 공통 배타 잠금을 유지한다. 잠금 순서를 정리해 주문과 구조 변경의 경합을 보호한다.
- 주문번호는 기존 `NEXT_DISPLAY_NUMBER` 행에서 별도 연결로 짧게 할당한다. 주문 본문 저장이 끝날 때까지 번호 행 잠금을 유지하지 않는다. 기존 번호 체계와 이전 리비전의 할당 방식에 호환되며, 주문 실패 시 번호가 비어 있을 수 있다.
- PostgreSQL 이벤트 수신과 번호 할당에 최대 2개의 별도 연결 풀을 사용한다. 일반 요청 풀은 기존 10개, 연결 확보 제한 3초를 유지한다.
- 직원 테이블 목록·주문 큐·청구 조회를 읽기 전용 트랜잭션으로 묶어 중첩 조회가 같은 연결과 일관된 스냅샷을 사용하게 한다.
- 연결 확보·자원 장애와 잠금 획득 실패는 `503 SERVER_BUSY`, `retryable=true`, `Retry-After: 1`로 응답한다. 주문 자동 재전송은 추가하지 않는다.

### 실시간 이벤트와 유휴 연결

- 이벤트 ID 생성 직전의 짧은 잠금으로 커밋 순서와 SSE 커서 순서를 맞춘다. 롤백된 주문의 이벤트는 발행하지 않는다.
- 이벤트 수신기는 알림마다 개별 조회하는 대신 커밋된 이벤트를 ID 순서대로 최대 250개씩 읽는다. 직원 화면 갱신은 고정 100ms 창으로 합쳐 주문 집중 시 재조회 횟수를 줄인다.
- 고객이 메뉴 목록·상세 화면에서 5분간 조작하지 않으면 SSE·정기 조회·재접속 예약을 멈춘다. 다시 조작하면 메뉴와 주문 조회를 재개하며 카트와 테이블 인증은 유지한다.
- 카트·주문 확인·주문 현황·완료·이벤트 주문 및 직원 화면은 고객 유휴 중지 대상에서 제외한다. 연결·조회 재개 시점을 분산하되 실제 주문 전송은 지연하지 않는다.
- 잠금 대기·유지 시간, 주문번호 할당, 연결 풀, 고객·직원 SSE 연결 수 지표를 추가한다.

### 예약 전 인스턴스 준비

- Terraform에서 최소·최대 인스턴스와 동시 요청 한도를 변수로 관리한다. 기본값은 최소 1, 서비스·리비전 최대 5, 동시 요청 100이다.
- `reservation-capacity.py`에 `prepare`, `status`, `restore`를 추가한다. 예약 전에 최소 인스턴스를 2개 또는 3개로 조정하고 이전 값으로 복원할 수 있다.
- 변경 전 상태 저장, 중복 실행 방지, 원격 동시 변경 감지 및 복원 전 리비전·트래픽 확인을 적용한다. 설정 반영 후 실제 인스턴스 준비 상태를 확인하는 운영 절차를 문서화한다.
- 인스턴스당 앱 연결 예산은 최대 12개, 5개 기준 60개다. 운영 DB의 연결 상한 100개 내에서 시스템 연결·예약 연결·운영 여유와 배포 중 리비전 중첩을 함께 확인해야 한다.

### 메뉴 이미지 호환

- 서버 이미지 URL이 없는 소주·맥주에 첨부 이미지 기반 기본 이미지를 표시한다. 기존 공통 이미지 컴포넌트의 전체 병 표시와 로딩 실패 대체 표시를 유지한다.
- `dev`에 반영된 메뉴 이미지 작업과 통합했으며 서버에 지정된 이미지 URL을 우선한다.

## 검증

2026-09-17 충돌 병합 후 백엔드 41개, 프런트엔드 34개, 운영 도구 5개 테스트가 통과했다. 프런트엔드 ESLint·프로덕션 빌드와 Terraform 검증도 통과했다. 이후 최신 `dev` 병합은 메뉴 이미지 자산·도구·문서 변경이며 아래 시험 대상 애플리케이션 코드는 동일하다.

PostgreSQL 17 Testcontainers와 개발 머신의 실제 HTTP 서버에서 고객 SSE 100개·직원 SSE 4개를 유지하고 검증했다.

| 시나리오 | 결과 |
|---|---|
| 서로 다른 테이블 50명 동시 주문 × 3회 | 150건 모두 성공, 회차별 p95 154~193ms |
| 같은 테이블 50명 동시 주문 | 50건 모두 성공, p95 323ms |
| 50명 주문 + 50개 동시 조회 | 모두 성공, 주문 p95 257ms / 조회 p95 309ms |
| 예약 고객 40명 주문 + 조회 × 3회 | 모두 성공, 주문 p95 135~275ms |
| 주문 트랜잭션에 합성 지연 100ms 추가 | 50건 모두 성공, p95 854ms |
| 이벤트 전달과 연결 정리 | 직원 4개 스트림 각각 주문 이벤트 420개 순서대로 수신, 고객 연결 40개 종료 후 100→60 감소 |

동일 요청 재전송, 요청 내용 충돌, 주문과 합석·분리·이동·결제·초기화의 경합, 롤백 시 이벤트 미발행, 실제 연결 풀 고갈 후 503과 재시도 복구도 검증했다. 프런트엔드는 유휴·숨김·복귀·페이지 이동·재접속 중지 및 직원 갱신 묶음을 검증했다.

**위 결과는 로컬 검증이며 운영에서 50명 동시 주문을 보장하는 수치가 아니다.** Cloud Run과 동일 사양에서 최소 인스턴스 1/2/3개 비교, 10분 지속 부하, 실제 지표 확인 및 범위를 제한한 운영 재검증이 남아 있다.

## 배포 및 운영 확인

- 이번 변경 자체에 추가 DB 스키마 마이그레이션은 없다. 일반 요청 풀을 늘리거나 운영 최소 인스턴스를 실제 변경하지 않았으며 예약 자동 일정도 생성하지 않았다.
- 배포 후 연결 풀 대기·타임아웃, 잠금 대기, 주문 지연, SSE 전달·정리와 실제 DB 연결 수를 확인한다. 직원 변경 작업의 공통 잠금과 주문 큐의 조회 비용은 후속 측정 대상이다.
- 예약 준비 수량은 동일 사양 검증 후 결정한다. 준비 도구의 성공만으로 준비 완료로 판단하지 않고 적용 후 인스턴스 지표와 정상 시작을 확인한다. 피크 종료 후 저장된 상태로 복원한다.
- 코드 복구 시 이전 호환 리비전으로 되돌리고, 최소 인스턴스는 준비 도구의 복원 절차를 따른다. 이미 할당된 주문번호는 되돌리지 않는다.
