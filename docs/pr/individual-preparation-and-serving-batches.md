# 메뉴 1개 단위 조리와 완료 시점별 서빙 카드 분리

기존 신규 주문의 체크박스는 선택한 메뉴 수량 전체를 조리 완료 처리했고, 나중에 완료된 음식도 같은 주문의 서빙 카드에 합쳐졌다. 신규 주문에서는 선택한 1개만 조리 시작하고, 조리 중에서는 선택한 1개만 완료한다. 완료 요청마다 별도 서빙 카드를 만들고 해당 카드에 표시된 항목만 서빙 완료 처리한다.

## 동작

- 같은 메뉴 3개도 주방에서는 `×1` 세 줄로 표시하며 각 줄의 상태를 독립적으로 관리한다.
- `전체 조리 시작`은 신규 카드의 항목만, `전체 완료`는 조리 중 카드의 항목만 처리한다. 같은 주문이 신규와 조리 중에 동시에 표시될 수 있다.
- 개별 완료는 별도 카드, 한 번의 전체 완료로 처리한 항목은 한 카드다. 같은 메뉴도 완료 시점이 다르면 합치지 않는다.
- 주류·음료·제조 음료는 기존처럼 주문 즉시 같은 서빙 대기 화면에 표시한다. 별도 준비 단계나 영역은 추가하지 않는다.
- 주방·서빙 배지는 표시 중인 카드 수를 기준으로 한다. 서빙 카드의 대기 시간은 그 묶음의 완료 시각 기준이다.
- 엽전 수령 전 서빙 완료 금지, 고객에게 실제 서빙 완료 표시, 원화·엽전 통계 및 할인 정책은 유지한다.

## 구현과 호환성

- V9의 `order_preparation_units`가 주문 수량만큼 처리 기록을 생성한다. `PENDING → COOKING → READY → SERVED` 상태와 완료 묶음 ID·시각을 저장한다. 기존 주문 항목과 수량·단가·금액은 변경하지 않는다.
- 기존 데이터는 항목 준비 상태를 옮기고, 기존 주문이 조리 중이면 아직 준비되지 않은 항목을 조리 중으로 이행한다. 기존 데이터에는 완료 버튼 클릭 이력이 없으므로 기존 서빙 묶음은 주문 ID와 준비 시각으로 복원한다.
- 새 주문과 서비스 주문에도 개별 기록을 생성한다. 조리 전 수량 수정 시 처리 기록을 함께 증감하고, 조리 또는 일부 서빙이 시작된 품목의 수량 변경·항목 취소를 차단한다.
- `POST /api/v1/staff/orders/preparation/transition`: `orderId`, `unitIds`, `action=START|COMPLETE|SERVE`. 직원 인증이 필요하다. 클라이언트가 보고 있던 항목 ID만 대상으로 처리한다.
- 완료 한 번마다 새 묶음 ID를 발급한다. 동일 요청 재시도는 이미 처리된 항목을 다음 상태로 넘기거나 새 묶음을 만들지 않는다. 일부 항목만 다른 기기에서 처리한 오래된 일괄 요청은 409로 거부하며 나머지를 변경하지 않는다.
- 준비 큐에 `cardId`, 항목별 `unitIds`를 추가한다. 조리 시작·서빙 완료는 주문 전체 대신 이 ID들을 전달한다.
- 기존 테이블 전체 상태 변경과 구버전 항목 완료 API는 개별 처리 기록과 동기화한다. 기존 테이블 전체 완료 동작은 유지하며, 새 주방·서빙 화면에서는 범위가 명확한 새 API를 사용한다.
- 변경 시 주문 SSE를 발행한다. 새로고침이나 기기 변경 후에도 DB의 개별 상태와 완료 묶음을 다시 읽는다.

## 검증

- PostgreSQL 통합 테스트 37개: 기존 회귀 및 1개 시작/완료, 별도 완료 묶음, 이전 카드만 서빙, 중복·동시 처리, 오래된 일괄 요청의 원자성, 다른 주문/묶음 ID 거부, 엽전 수령 제한, 수량 변경·취소, 과거 주문 마이그레이션.
- 프런트엔드 테스트 21개: 개별 시작, 완료 요청별 카드 분리, 선택 카드만 서빙, 신규/조리 중 체크박스 라벨 포함.
- ESLint, TypeScript/Vite 빌드 통과.
- 별도 로컬 PostgreSQL과 실제 Spring API에 연결한 브라우저에서 `짜계치 3 + 닭발 1 + 콜라 2` 주문을 검증했다. 짜계치 1개 개별 완료 후 나머지 전체 완료 시 음료/개별 완료/전체 완료가 3개 카드로 표시됐다. 개별 완료 카드만 서빙한 뒤 새로고침해도 나머지 카드가 유지됐다.

운영 배포·운영 DB 마이그레이션은 실행하지 않았다. V9 및 새 백엔드를 먼저 적용하고 새 POS를 배포해야 개별 처리 UI와 큐가 일치한다.
