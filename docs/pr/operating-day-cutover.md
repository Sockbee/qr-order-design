# 운영 시작 시 테스트 기록 소프트 삭제 및 통계 분리

2026-09-17 18:00(Asia/Seoul)을 실제 운영의 시작점으로 사용한다. 그 이전 주문·결제·서비스·정산·직원 호출·입장·합석 기록은 보존하면서 운영 화면에서 제외하고, 이후 주문만 판매 통계에 포함한다.

## 적용 범위

- 메뉴, 가격, 품절 여부, 이벤트 가격, 테이블 등록, QR 토큰, 학생회 명단, 로그인 설정을 유지한다.
- 주문·방문·호출에 `deleted_at`을 추가한다. 주문 항목과 개별 조리 상태, 결제 금액 및 입금자명 등 원본은 유지한다.
- 운영 조회와 변경은 `live_orders`, `live_table_sessions`, `live_calls`를 사용한다. 삭제된 방문은 새 방문 생성 시 유일성 제약에서 제외한다.
- 학생회 정산 상태는 `archived_staff_settlements`에 원본 행을 보존하고 미정산으로 초기화한다. 운영 시작 후 서비스 지급 내역이 없는 인원은 정산 목록에 표시하지 않는다. 서비스 제공 대상 명단에는 계속 표시한다.
- 주방·서빙·결제·호출·고객 주문 내역도 동일한 소프트 삭제 기준을 사용한다.
- 삭제된 테스트 주문/호출의 요청 ID를 재사용하면 `TEST_DATA_ARCHIVED`로 거절한다. 새 요청 ID로 정상 주문할 수 있다.
- 주문번호와 이벤트 순번은 재설정하지 않는다. 기존 기록과의 중복 및 SSE 누락을 방지한다.

## 전환 시각과 동시 요청

`operation_cutover`에 명시한 절대 시각을 기준으로 한 번만 전환한다. 마이그레이션에는 시각을 넣지 않아 코드 배포만으로 초기화되지 않는다.

- 서버가 1초 간격으로 전환 시각을 확인한다. 서버 유휴·재시작 시에도 API 요청 처리 전에 확인한다.
- 방문 변경과 동일한 DB 잠금 안에서 소프트 삭제, 정산 상태 보존·초기화, 완료 기록, SSE 이벤트를 한 트랜잭션으로 처리한다.
- 여러 서버가 동시에 실행해도 한 번만 적용한다. 실패하면 롤백하고 다음 확인 때 재시도한다.
- 운영 경계에 걸친 변경 요청은 재시도 가능한 `OPERATION_STARTING` 응답으로 보호한다.
- 시각 판정은 DB 시간이며, 실제 주문 집계 조건은 `created_at >= starts_at`이다. 정각 주문을 포함한다.
- 실시간 `operation.started` 이벤트가 열린 화면의 조회를 갱신한다. 정산 화면에도 실시간 갱신과 15초 재조회, 탭 복귀 갱신을 적용한다.

## 판매 통계

기존 날짜 필터 안에서도 운영 시작 이전 주문을 제외한다. 필터에서 과거 날짜를 선택해도 테스트 매출이 다시 포함되지 않는다. 할인·서비스·엽전 분류 및 금액 정책은 유지한다. 원화 합계의 할인 반올림 계산에도 테스트 주문을 포함하지 않는다.

통계 화면에 운영 집계 시작 시각을 한국 시간으로 표시한다. 시각을 예약하면 통계는 즉시 해당 시각 이후만 조회하며, 초기화 전 테스트 주문 화면은 예정 시각까지 유지한다.

## 검증

- 백엔드 44개 테스트 통과(통합 테스트 43개, 실제 HTTP 동시 고객 테스트 1개).
- 프런트엔드 34개 테스트, 린트, 운영 API 주소로 빌드 통과.
- 시각 이전에는 초기화되지 않음, 중복 실행 방지, 동시 초기화 요청, 정각 포함, 새 주문 유지 확인.
- 고객·주방·서빙·결제·정산·호출에서 테스트 기록 제외, 원본 행·메뉴 가격·QR·명단 보존 확인.
- 이전 요청 재전송 차단, 새 방문/주문 생성, 서비스·일반 매출 분리 확인.

## 예약 및 점검

`scripts/operating-day-cutover.py`는 기본 읽기 전용이다. Cloud SQL 프록시와 `psycopg`, 인증된 gcloud가 필요하며 비밀번호는 Secret Manager에서 메모리로만 읽는다.

```sh
python scripts/operating-day-cutover.py --schedule --starts-at '2026-09-17T18:00:00+09:00'
python scripts/operating-day-cutover.py
python scripts/operating-day-cutover.py --verify-after-start
```

예약 명령은 미래 시각만 받으며, 기존 예약 시각을 덮어쓰지 않는다. 전환 결과는 `operation_cutover.completed_at`, `archived_counts`, `OPERATION_STARTED` 감사 로그로 확인한다. 전환 후 실제 주문이 있을 수 있으므로 모든 화면이 0건인지만으로 성공을 판정하지 않고, 운영 이전 기록이 활성 조회에 남아 있는지 검사한다.

복구가 필요한 경우 보존된 원본과 정산 스냅샷을 기준으로 검토한다. 운영 주문이 생긴 뒤 `deleted_at`을 일괄 해제하면 새 방문과 충돌할 수 있으므로 실행 중인 운영에 무조건 복원하지 않는다.
