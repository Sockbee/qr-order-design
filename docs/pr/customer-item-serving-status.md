# 고객 메뉴별 조리·서빙 상태 표시

## 개요

POS에서 조리 완료를 누르면 고객에게 서빙 완료로 표시되던 상태 연결을 수정했다.
고객 주문내역에 메뉴별 `조리 중`·`서빙 완료` 태그를 추가하고, 상단 진행 단계를
`접수됨 → 조리 중 → 서빙 완료`로 줄였다.

## 변경 사항

| POS 처리 | 메뉴 상태 | 고객 표시 |
|---|---|---|
| 주문 접수 / 조리 대기 | `PENDING` | 메뉴는 조리 중, 전체 주문이 접수 상태이면 상단은 접수됨 |
| 조리 완료 / 서빙 대기 | `READY` | 조리 중 |
| 서빙 완료 | `SERVED` | 서빙 완료 |

- 고객 목록·단건·접수 응답의 메뉴에 `preparationStatus`를 포함하고, 프런트에서 주문별 메뉴 상태를 유지한다.
- `CustomerOrderStatus`가 내부 주문 상태 `SERVING`을 `preparing`, `COMPLETED`를 `served`로 변환한다.
  조회 응답도 내부 상태에서 다시 계산하므로 과거의 `public_status`가 남아 있어도 새 기준으로 표시한다.
- 일부 메뉴만 서빙한 주문은 남은 메뉴의 조리 상태를 유지한다. 준비된 메뉴가 없는 주문에
  서빙 완료 요청이 들어와도 아직 조리 중인 메뉴를 완료 처리하지 않는다.
- 상단은 취소되지 않은 현재 주문 전체를 집계한다. 새 주문만 서빙됐더라도 이전 주문의
  메뉴가 남아 있으면 조리 중이며, 모두 서빙됐을 때만 서빙 완료가 된다.
- 이전에 저장된 `closed` 주문은 고객에게 서빙 완료로 표시한다. 별도의 완료 단계는 없다.
- 메뉴 태그는 기존 `OrderStatusChip`의 색상과 텍스트를 재사용하고, 서비스 메뉴의 정상가·0원 표시를 유지한다.

## Figma

이번 변경은 사용자 요청에 따른 고객 화면 수정으로, 기존 Tailwind 컴포넌트와 디자인 토큰을 사용했다.
Figma 화면과 POS의 조리 완료·서빙 완료 버튼 및 작업 구분은 변경하지 않았다.

## 검증

- 프런트엔드: `npm run lint`, `VITE_API_BASE_URL=http://localhost:8080 npm run build` 통과.
- Vitest: 11개 테스트 통과. 메뉴 상태 변환, 전체 주문 집계, 3단계 표시,
  서비스 가격 표시, 기존 API 응답 및 재조회 상태 호환을 검증했다.
- 백엔드: Java 21 / PostgreSQL Testcontainers 통합 테스트 20개 통과.
  조리 완료와 서빙 완료, 일부 메뉴 서빙, 테이블 일괄 처리, 조리 완료 취소,
  과거 상태값이 남은 주문의 목록·단건 조회를 검증했다.
- 로컬 고정 데이터로 고객 화면을 390×844 및 320×740에서 확인했다.
  같은 주문 안의 서로 다른 메뉴 태그, 서비스 메뉴, 3단계 현황이 표시되며 가로 넘침이 없다.

## 참고 사항

- 작업 브랜치: `feat/customer-item-serving-status` (`dev`의 현재 통합 코드에서 분기).
- 실제 메뉴별 구분을 위해 프런트엔드와 백엔드를 함께 배포해야 한다.
  메뉴 상태 필드가 없는 이전 API 응답은 해당 주문의 상태로 표시한다.
- DB 스키마 변경은 없다. 운영 배포는 별도로 진행한다.
