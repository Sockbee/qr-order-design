# 메뉴별 판매 통계와 입금자명 기록

브랜치: `feat/menu-statistic`

주문 접수 직후에는 일반가로 판매 통계를 집계하고, 학생회비 할인 결제가 완료되면
해당 주문을 납부자 유형으로 옮겨 할인된 금액을 표시한다. 서비스는 별도 유형으로
유지하며, B03 입금 확인에는 입금자명 필수 입력을 추가했다.

## 화면

- POS 공통 메뉴에 **판매 통계**(`/staff/sales`)를 추가했다.
- 메뉴를 접으면 일반·납부자·서비스의 판매량과 판매금액 합계를 표시한다.
- 펼치면 **일반 테이블 → 학생회비 납부자 → 서비스** 순서로 수량·금액·적용 할인율을 표시한다.
- 시작일/종료일, 오늘/최근 7일, 카테고리, 메뉴명 검색, 수량/금액 내림차순 정렬을 지원한다.
- 합계 카드도 현재 조회 조건에 맞춰 계산한다. 로딩·오류·빈 결과는 별도로 표시한다.
- B03에서 입금자명 1~100자를 입력해야 확정할 수 있다. 실패하면 입력을 유지하고 재시도할 수 있다.
- 결제 완료 카드에 입금자명, 확인 기기, 확인 시간을 표시한다. 기존 인증은 개인 계정이 아닌
  운영 기기 인증이므로 `paymentConfirmedBy`는 로그인한 **기기 라벨**이다.

디자인 기준: [판매 통계 펼침](https://www.figma.com/design/u5pXNGrYEdVDbvqmJLglUS?node-id=371-4929),
[입금 확인](https://www.figma.com/design/u5pXNGrYEdVDbvqmJLglUS?node-id=365-5234).

## 집계 정책

| 유형 | 분류 시점 | 집계 금액 |
|---|---|---|
| 일반 | 미결제 손님 주문, 할인 없이 결제한 손님 주문 | 주문 항목에 저장된 일반가 |
| 학생회비 납부자 | 할인율이 0보다 큰 손님 결제 확정 후 | 결제 시 저장한 할인율을 적용한 금액 |
| 서비스 | 서비스 주문 접수부터, 정산 여부와 무관 | 서비스 주문 당시 저장한 할인율을 적용한 부담금 |

학생회비 납부자가 절반 이상인 테이블에 20%를 적용하는 운영 기준은 유지한다.
입장 시/결제 시 할인 여부를 선택할지는 아직 미확정이므로 기존 수동 할인 기능을
사용한다. 테이블에서 미리 할인을 선택했어도 결제 전 통계는 일반가로 유지한다.
서비스 할인율은 기존 `STAFF_DISCOUNT_RATE` 설정(기본 20%)을 사용하며 테이블 할인과 독립적이다.
이후 설정을 변경해도 기존 주문의 서비스 할인율과 확정된 손님 결제 할인율은 바뀌지 않는다.

조회 기간은 양 끝 날짜를 포함하고 최대 366일이다. `TIME_ZONE` 설정(현재 `Asia/Seoul`)의
**주문 생성일**로 조회한다. 다른 날짜에 결제해도 원래 주문 날짜의 통계를 재분류한다.
취소 주문, 취소 항목, 환불 주문은 제외한다. 미결제 일반가와 미정산 서비스 부담금도
포함하므로 이 화면은 입금 완료액만을 나타내는 현금 수납 장부가 아니다.

할인액은 기존 결제와 동일하게 정가 합계에 할인율을 곱한 뒤 원 미만을 버린다.
메뉴별 금액은 청구 단위 안에서 주문일·주문 ID·항목 순서에 따라 누적 할인액의 차이로
배분한다. 합석은 대표 세션 청구 단위, 서비스는 서비스 주문 단위로 계산하므로,
메뉴별 금액 합계와 실제 청구액이 일치한다. 기간 필터를 적용하기 전에 배분하여
여러 날짜에 걸친 합석 주문도 기간별 금액의 합이 전체 금액과 일치한다.

## API와 저장

- `POST /api/v1/staff/sales/menu`: 기존 스태프 Bearer 인증, 요청은
  `{ "startDate": "2026-09-14", "endDate": "2026-09-14" }`.
  응답 `rows`는 메뉴·유형·할인율별 `quantity`, `amount`, `unpaidQuantity`와
  `menuId`, `name`, `categoryId`, `categoryLabel`, `type`, `discountRate`를 포함한다.
- 기존 `POST /api/v1/staff/tables/confirm-payment`에 `payerName`을 필수로 추가했다.
  세션/금액 검증, 입금자 기록, 합석 세션 종료, 손님 주문의 결제 할인율 저장은
  한 트랜잭션으로 처리한다. 같은 요청 ID 재시도는 이름까지 일치해야 성공한다.
- 결제 대기열 응답에 `payerName`, `paymentConfirmedBy`, `paidAt`을 추가했다.
- 프런트엔드는 주문 이벤트와 15초 주기 갱신을 사용한다. 숨겨진 화면의 주기 조회는 멈춘다.
  API를 연결하지 않은 개발 환경에서만 디자인 예시 데이터를 표시한다.

Flyway `V6__payer_and_sales_discount_snapshots.sql`은 `table_sessions.payer_name`,
`table_sessions.payment_confirmed_by`, `orders.paid_discount_rate`를 추가한다.
기존 결제의 할인율은 저장된 대표 세션 할인율로 채운다. 과거 입금자명과 확인자는
추정하지 않고 null로 남겨 화면에 `기존 기록 없음`으로 표시한다.

배포 시 백엔드의 V6 마이그레이션과 프런트엔드를 함께 반영해야 한다.
업데이트 전 클라이언트는 필수 `payerName`을 보내지 않아 입금 확인 요청이 거절된다.

## 검증

- Java 21, 실제 PostgreSQL Testcontainers 통합 테스트 **23개 통과**.
- 프런트엔드 Vitest **14개 통과**, TypeScript/Vite 프로덕션 빌드 및 ESLint 통과.
- 결제 전후 유형 이동, 미리 선택한 할인 미반영, 서비스 할인율 20%/50% 이력,
  취소 제외, 합석 결제, 한국 시간 자정 경계, 원 단위 배분, 기간 검증을 확인했다.
- 입금자 공백 거절, 저장 값, 결제 요청 재시도/충돌, 인증 누락 및 OpenAPI 계약을 확인했다.
- 로컬 브라우저에서 소주 펼침과 검색 결과 합계, 입금자명 필수 입력 및 완료 기록을 확인했다.

로컬 검증이며 운영 배포나 GitHub PR 생성은 이 작업에 포함하지 않았다.
