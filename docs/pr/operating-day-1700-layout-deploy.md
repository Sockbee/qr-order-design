# 초기화 시각을 17시로 변경하고 최신 테이블 배치 적용

운영 전 테스트 기록 초기화와 판매 통계 집계 시작을 2026-09-17 **17:00(Asia/Seoul)**으로 앞당긴다. 같은 날 전달받은 새 배치도를 모든 테이블 선택 화면에 적용하고, 자동 배포의 동시 주문 테스트 실패를 해결한다.

## 초기화 예약

- 실제 DB의 `operation_cutover.starts_at`을 `2026-09-17T09:00:00Z`에서 `2026-09-17T08:00:00Z`로 변경했다. 판매 통계도 같은 값을 사용한다.
- 예약 변경 당시 `completed_at`은 NULL이었다. 주문 73건·방문 31건·호출 2건은 그대로 유지됐고, 메뉴 17개·테이블 30개·학생회 명단 30명도 유지됐다. 초기화는 예약 시각에 서버가 수행한다.
- 기존 18:01 결과 확인 자동화는 17:01로 변경했다. 이는 초기화 실행이 아닌 결과 확인용이다.
- 스크립트에 `--reschedule-from`을 추가했다. 지정한 기존 시각이 DB와 일치하고, 기존·새 시각 모두 미래이며, 전환이 완료되지 않은 경우에만 변경한다. 기존 예약 생성 명령으로는 다른 시각을 덮어쓸 수 없다.
- 예약 변경은 방문 변경과 동일한 DB 잠금 안에서 실행하고, 이전·새 시각을 `OPERATION_CUTOVER_RESCHEDULED` 감사 로그에 남긴다.

이번에 실행한 예약 변경 명령:

```sh
python scripts/operating-day-cutover.py --schedule \
  --reschedule-from '2026-09-17T18:00:00+09:00' \
  --starts-at '2026-09-17T17:00:00+09:00'
```

이미 변경 완료했으므로 위 명령을 재실행하면 기존 시각 불일치로 거절한다. 점검에는 인자 없는 조회 또는 시작 시각 이후 `--verify-after-start`를 사용한다.

## 테이블 배치

창문 기준 도면에 맞춰 다음과 같이 변경했다.

- 왼쪽 아래 T01, 그 오른쪽 위 T02, 왼쪽 중간 이벤트 공간.
- 아래 줄 왼쪽부터 T03·T04·T05(사각), T06·T07(원형).
- 중간 아래 줄 T08·T09·T10(원형), T11(마름모).
- 중간 위 줄 T12·T13·T14(원형), T15(마름모).
- 위쪽 T16·T17·T18(사각).
- 오른쪽 T19~T21, 그 아래 T22~T23은 기존처럼 각 4인 테이블로 유지.

기본 POS 화면은 도면의 180도 회전 배치이며, `보기 방향`에서 창문 기준으로 전환할 수 있다. 공유 배치 데이터를 사용하므로 테이블 홈·상세 뒤 배경·합석·이동 선택에 함께 반영된다. 테이블 ID·QR·주문 기록은 변경하지 않으며 이벤트는 주문할 수 없는 표시다.

## 배포 실패 조사

- 실패 빌드: `8d909e6b-c0b8-4da5-8fb0-5b28e6cdfa66`.
- `backend-tests` 단계의 `FiftyCustomerCapacityTest` 147행에서 DB 연결 대기 시간 초과가 발생했다. 주문 묶음의 응답 검증 후 주문 수를 조회하는 지점이며, 프런트엔드 빌드·서비스 배포 단계에는 도달하지 않았다.
- 초기화 기능 도입 전 빌드 `45662da8-2666-41b4-8b72-2ec2b4e6cb79`에서도 같은 실패가 발생했다. 로컬에서 같은 전체 테스트를 재실행하면 44개 모두 통과했다.
- HTTP 서버·PostgreSQL·100개 고객 SSE 연결·동시 주문을 함께 실행하는 Cloud Build 작업자를 `E2_HIGHCPU_8`로 변경했다. 테스트 수와 DB 연결 대기 제한(3초)은 유지한다.
- 실패 시 테스트 XML을 빌드 로그에 출력해 연결 풀 상태·전체 예외·부하 측정 결과를 확인할 수 있도록 했다.
- 확장 작업자의 재실행에서 주문 420건과 직원 4명 각각의 SSE 420건 수신은 통과했지만, 직원 조회 4건이 HTTP 401로 실패했다. 토큰 검사에서 DB 연결 예외까지 잘못된 토큰으로 변환하던 것이 원인이었다.
- DB 연결 부족은 `503 SERVER_BUSY`, `retryable=true`, `Retry-After: 1`로 응답하도록 수정했다. 잘못된 토큰은 계속 401로 거절하고, 연결이 복구되면 기존 정상 토큰으로 다시 조회할 수 있다.
- 부하 테스트는 직원 화면마다 조회 하나만 진행하고, 그동안 도착한 갱신 이벤트는 다음 조회로 합친다. 기존 테스트의 100ms 주기 비동기 조회가 느린 DB에서 제한 없이 누적되던 것을 수정했다. 100개 SSE 연결·동시 주문·동시 조회·중복 방지·420건 알림 검증과 성공 응답 조건은 유지한다.
